# The build version has one source and the precache list comes from the build output

Every release used to edit the same five places by hand (the CHANGELOG heading, `package.json`, both root versions in `package-lock.json`, `BUILD` in `src/main.js` and `CACHE_VERSION` in `sw.js`), while the prerendered home footer already read `package.json` at build time, so one missed edit made the footer change version as the page script took over, and no check caught it. The service worker precache list was every `.js` file in `dist/assets`, which also picked up twelve stale bundles kept in `public/assets/` since v1.10.5 to cover the CDN/HTML update gap; nobody had refreshed them since, so they protected no live version and made up 46% of a first install. We made `package.json` the only place the version is written: `vite.config.ts` reads it once and gives `v` plus the version to the prerendered footer, to the page as the compile-time constant `__BUILD_VERSION__` (Vite `define`, declared in `src/build/build-version.d.ts`), and to `dist/sw.js`, where the existing copy step replaces the `CACHE_VERSION` and `VITE_BUILD_ASSETS` placeholders through the pure `injectServiceWorker` in `src/build/service-worker.ts`, failing the build and naming the placeholder when either is missing. `npm version <bump> --no-git-tag-version` keeps `package-lock.json` in step, and `tests/version-consistency.test.ts` checks that the newest CHANGELOG heading and both lock fields equal `package.json`. The precache list is now derived from the output bundle by the pure `precacheAssets`: the files `index.html` references, every chunk reachable from them by static or dynamic import, and the files their CSS references with `url()`; `public/assets/` was deleted.

## Considered Options

- **Workbox or `vite-plugin-pwa`.** Rejected: the whole `sw.js` would be rewritten to reproduce its navigation network-first, runtime font cache and `CACHE_URLS` message; Workbox names its caches `workbox-precache-*`, so the `horo-guide-*` cleanup on activate would need a migration for installed users; and the minified worker would break the release readback that greps `^const CACHE_VERSION` from the live `sw.js`. It also adds a dependency.
- **Let Vite bundle `sw.js` (a Rollup input or `?worker&url`) and use `define` there too.** Rejected: Vite would hash, minify and move the worker into `assets/`, but a service worker's URL must stay fixed at the site root for its scope and update check, and the plain `CACHE_VERSION` line the readback relies on would disappear.
- **Write the version into `src/main.js` and `sw.js` at build time with a script, or check the five places in the build.** Rejected: the source would still carry a version that can be stale, and a build-time check fails a build for a documentation mismatch; a test catches the same mismatch in PR CI and before deploy.
- **Keep scanning `dist/assets` and only delete the stale bundles.** Rejected: anything placed in `public/assets/` would again be precached silently; the bundle graph lists exactly what this build emitted and the page can load.

## Consequences

- A release edits only `package.json`/`package-lock.json` (through `npm version`) and `CHANGELOG.md`; `src/main.js` and the root `sw.js` hold no version, and the root `sw.js` is a template whose placeholders only `npm run build` fills in. The service worker is not registered in dev, so the placeholder is never served.
- `dist/sw.js` stays a plain, unminified file at the site root with one `const CACHE_VERSION = "vX.Y.Z";` line, so the release skill's live readback is unchanged.
- The precache list is the same as before minus the twelve stale bundles. Song chunks are still covered because each song is a dynamic import of the entry chunk (ADR 0001). CSS imported only by a lazily loaded chunk (the Waline board's stylesheet) and files referenced only from `<meta content>` (the Open Graph image) are not precached, as before; they are cached at runtime when first fetched.
- The CDN/HTML update gap the stale bundles were meant to cover is accepted: it lasts minutes, installed service workers serve navigation network-first with a cached fallback, and the gap has been uncovered since v1.11 with no reports.
- Pull requests run `.github/workflows/ci.yml` (typecheck, test, build and `git diff --check` over the PR range) with read-only permissions and a per-PR concurrency group; `pages.yml` keeps its own checks before deploy and runs only on a push to `main` that changes `package.json` (a release) or on manual dispatch, since a merge without a version bump keeps the same `CACHE_VERSION`.
