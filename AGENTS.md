# Project instructions

This is a Vite static PWA for a Vaundy fan guide. Work from source files; `dist/` is generated output. Preserve existing user changes and keep each patch limited to the requested scope.

## Commits and versioning

- Use Conventional Commits for every commit: `<type>(<scope>): <summary>`, with an optional scope. Use `feat` for user-visible functionality, `fix` for bug fixes, and `docs`, `refactor`, `style`, `perf`, `test`, `build`, `ci`, or `chore` for the corresponding work. Keep release commits exactly `chore(release): publish guide vX.Y.Z`; use `docs(changelog): link vX.Y.Z release commit` for the follow-up changelog link commit.
- Select the SemVer bump from the complete release scope before editing version markers. Use a `MAJOR` bump for breaking or incompatible changes, a `MINOR` bump for a new backward-compatible user-visible capability or substantial feature, and a `PATCH` bump for fixes, content or timing corrections, documentation, styling, refactors, and maintenance without a new capability. A large feature such as a new desktop mode must advance the minor version, for example `1.8.x` to `1.9.0`.
- Write the version only in `package.json`, with `npm version <bump> --no-git-tag-version`, which also updates both root version fields in `package-lock.json`; the build injects it into `src/main.js` (`BUILD`, through Vite `define`), the service worker's `CACHE_VERSION` and the prerendered footer, so do not write a version in `src/main.js` or `sw.js`. Write the matching changelog heading by hand; `npm test` fails when the changelog heading or `package-lock.json` disagrees with `package.json`. Done when the commit subjects and version bump match the release scope.

## Workflow

1. Inspect `git status --short --branch`, the relevant files, and `package.json` before editing. Read `DESIGN.md` for visual or accessibility work and the relevant `README.md` section for user-facing behavior. Done when the affected files and verification command are clear.
2. Edit the source of truth: song identity in `src/song-metadata.js` (authoritative; keep the copied fields in `src/song-lyrics.js` identical; write `title` as `中文譯名 (日文原題)`, and as the Japanese original alone when it is all kanji, optionally joined by の, or an English word or phrase, e.g. `前前前世`, `怪獣の花唄`, `replica`, also `融解sink`; romanized or mixed originals keep the Chinese title, e.g. `心動 (Tokimeki)`, `GORILLA 戲碼 (GORILLA芝居)`); lyrics, translations and timing in `src/song-lyrics.js`; Japanese chant cues in `src/chant-guide.js`; BPM, setlist and other show data in `src/data.js`; readings in `src/furigana-corrections.js` and `furigana.js`, keyed by the exact full lyric line text, so a lyric text edit moves its reading keys too; per-word karaoke timing in `src/word-timing.js` (generated by `scripts/word-timing/build-word-timing.mjs`; row times are join keys, so retiming a row moves its word-timing key too); the live karaoke timing lookup for songs without bundled timing in `karaoke-sources.js`; app behavior in `src/main.js`, which reads songs only through `src/catalogue/` (`list`, `get`, `load`); lyric row markup and the row state during playback (current line, in-view, karaoke units and progress, scrolling) in the lyric view `src/lyric-view/`, which the song page and the Document PiP window (`src/document-pip.js`) change only through their own mount; shared lyric text helpers in `src/ui/text.ts`; styles and icons in `src/*.css` and `src/ui/icons.js`; caching and packaging in `sw.js`, `vite.config.ts` and `src/build/` (service worker version injection and the precache list derived from the build output, see `docs/adr/0003-build-version-and-precache-from-build.md`). Song list marks and numbers are derived; do not hand-maintain them. Use the terms in `CONTEXT.md` and keep the decisions in `docs/adr/0001-song-catalogue-assembled-at-build.md`, `docs/adr/0002-lyric-view-rendered-once-mounted-twice.md` and `docs/adr/0005-bundled-word-timing.md`. Preserve the spoiler gate and the non-official status of reference setlist data. Done when the intended source files express the complete change.
3. Verify the result: run `npm run typecheck`, `npm test` and `npm run build` for any song data or application change (the build fails on a violated song data rule and names the song, line and rule), and `git diff --check` for every text change; the CI workflow (`.github/workflows/ci.yml`) runs the same checks on every pull request. When a song data change intentionally alters `tests/__snapshots__/song-catalogue.golden.txt`, update it with `npx vitest run -u` and review that diff. Inspect the final diff and status. Done when all applicable checks pass and only intentional files changed.

## Explicit release requests

When the user asks to publish, release, or deploy:

1. Inspect status, remotes, and the intended release branch; resolve release scope before staging. Done when unrelated work is excluded.
2. Update `CHANGELOG.md` from the complete release scope. Use Traditional Chinese, follow its existing version-commit boundary and link format, put the newest section at the top, and cover every user-visible change in the release. Resolve every song name through the Japanese original title in `src/data.js` (for example, `〈不可幸力〉` and `〈恋風邪にのせて〉`) before writing it. Attribute every user-visible bullet to its responsible PR with a linked `[PR #N]`. Add a separate thank-you bullet only for external contributors, linking their handle and PR; the owner's own PRs (`@watain666`) need only the change description and PR link. When an older PR is already covered by an existing version, add its linked attribution to that version section instead of creating a duplicate release entry. Done when every bullet is traceable to a linked PR, external contributor thanks use linked handles and PRs, the new section is complete, uses Japanese song titles, and contains no placeholder commit links.
3. Apply the SemVer bump selected above with `npm version <patch|minor|major> --no-git-tag-version`, which updates `package.json` and both root version fields in `package-lock.json`; the build injects the version into `BUILD`, `CACHE_VERSION` and the prerendered footer. Done when `npm test` passes, which confirms the changelog heading, `package.json` and `package-lock.json` agree.
4. Run `npm run build` and `git diff --check`. Done when both succeed.
5. Stage only the approved release files and create `chore(release): publish guide vX.Y.Z`. Then create a follow-up `docs(changelog): link vX.Y.Z release commit` that links the changelog heading to the release commit's final full SHA; do not amend the release commit to include its own SHA. In this checkout, `origin` (`watain666/Vaundy-Taiwan-2026`) is the release repository; `upstream` (`limskyy123456-sudo/Vaundy-Seoul-2026`) is the source guide and is not a release target. Push both commits to `origin/main` and verify that branch contains them and the changelog points to the release commit. Done when the remote readback matches; report the version, release subject, and commit URL only then.
