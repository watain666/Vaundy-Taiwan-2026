# Per-word karaoke timing is bundled with the songs and joined at build time

Karaoke word highlighting depended on fetching timed lyrics in the browser: `karaoke-sources.js` asked the Beautiful Lyrics worker (`lyrics.txw.qzz.io`), AMLL TTML DB and LRCLIB for each song, then matched the provider's text to the page's lyric rows with `alignToLocalLyrics`. The worker is now blocked by Cloudflare and its fallback needs a Spotify token, so most songs fell back to the BPM estimate, and every song needed the network at least once. We now bundle vetted third-party word timing (KuGou KRC and similar), converted to the YouTube video's clock, in `src/word-timing.js`, generated by `scripts/word-timing/build-word-timing.mjs`. `assembleCatalogue` joins each entry to the lyric rows by the row `time` in hundredth-second buckets, as it does for chant cues, and attaches `line.words` and `song.wordTiming`; five build rules (`word-timing-unknown-song`, `word-timing-dead-key`, `word-timing-text-mismatch`, `word-timing-order`, `word-timing-start-offset`) fail the build and name the song and line. The page's `loadSongKaraokeTiming` (`src/services/karaoke-timing.ts`) builds the aligned timing directly from `line.words` for a song that has it, without loading or calling the network adapter; songs without bundled timing keep the live chain unchanged.

## Considered Options

- **Keep fetching at runtime and only replace the dead worker.** Rejected: every remaining provider is a third-party service that can disappear or start requiring credentials, the result is only as good as the runtime text match, and a first visit offline still has no timing.
- **Ship the provider files and align them in the browser with `alignToLocalLyrics`.** Rejected: alignment errors (a romaji provider line, a merged or split line) would surface only when someone opened the song; converting once and checking the words against the row text at build time catches them before deploy.

## Consequences

- Row times are join keys for word timing as well as for chant cues: retiming a lyric row without moving its key in `src/word-timing.js` is a build error (`word-timing-dead-key`), and a lyric text edit fails `word-timing-text-mismatch` until the words are regenerated.
- Regenerating or adding a song's word timing needs the script and its provider input; `src/word-timing.js` is not edited by hand.
- Word timing ships inside each song's chunk, so it is precached with the song and works offline; the golden snapshot records `wordTiming: matched/rows (source sourceId)` per song.
- `karaoke-sources.js` and its localStorage cache (`CACHE_VERSION`) only serve songs without bundled timing; the Document PiP gets the same timing because it reads the page's `karaokeTiming` through its own lyric view mount.
